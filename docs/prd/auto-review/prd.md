# 校閲の自動起動（auto-review）

関連 PRD: [note-inline-review](../note-inline-review/prd.md)

## Problem

v1 の校閲は、書き手がサイドパネルの「見直す」を押したときだけ動く。書き手は指摘を適用し、本文を直し、また「見直す」を押して次の指摘を確かめる、という往復を記事ごとに行う。押し忘れれば古い指摘が残り、押しすぎれば書き途中の原稿に対する指摘と費用が無駄になる。「いつ見直すか」の判断そのものが書き手に残っているのが課題である。

なお、「自動で動いてほしい」は体験の要望であって、無制限に動くことが目的ではない。執筆中に校閲が頻繁に起動すると、書き途中の文への指摘で表示が頻繁に更新され、推敲を妨げるおそれがある。また、原稿の外部送信と課金が繰り返されるため、起動頻度には制限が要る。本機能の検証仮説は「起動時期の判断を書き手から取り除いても、指摘を確認する負担と費用を増やさない」である。

現行実装では、校閲後に指摘の対象箇所が編集されると、その指摘は適用不能として表示される。つまり「結果が古いか」の判定はあるが、「いま校閲を走らせるか」の判断は存在せず、編集後に再び校閲するタイミングは書き手が見ている。後者を担うのが本機能である。

起動判断には、編集の区切りを信号（無入力時間・文量の変化など）からコードで決める方式と、「この段落は書き途中か」「前回の校閲から意味のある変更が入ったか」といった意味判断を判定モデルに委ねる方式がある。後者の候補は TypeSafe の Jev で、採否は実測による比較で決める。どちらを採るかは本 PRD の範囲で未決であり、評価計画（後述）に従う。

この課題を今扱う理由は、v1 の実装（PR #7 系の作業）で「見直す」の往復が実際に発生し、作者自身が押す手間を負っている段階だからである。起動の自動化は結果表示や適用の設計（v1 で確定済み）に依存するので、v1 の上に乗る独立した機能として扱う。

## 導出

`## Story`（repo root `AGENTS.md`）の Core action「書いている原稿にレビューをかけて指摘を見る」の「かける」操作を、書き手の明示操作から原稿の状態に応じた自動起動へ移す機能である。

## Overview

原稿を編集すると、推敲の区切りで校閲が自動起動し、手動の「見直す」と同じパネルと本文マークに指摘が表示される。自動起動の完了でパネルが開いたり入力位置が動いたりすることはなく、新しい指摘が届いたことは目立たない表示で分かる。自動送信を含む説明をインストール前に提示した利用者では自動起動を既定で有効とし、書き手は拡張全体に作用する一時停止・無効化でいつでも止められる。手動の「見直す」も引き続き使える。修正の適用は引き続き書き手の明示操作でのみ行われる（自動適用はしない）。

自動起動は標準モード（ログイン不要・提供者側の費用）と BYOK（書き手自身の API key を使う方式）の両方で、利用者に追加の key を求めずに動かす。標準モードでは恒常的な回数上限を設けずに済むよう、起動判断と校閲送信の両方で費用の小さい方式を選ぶ。障害時・異常な頻度への安全弁としての停止機構は残す。外部送信の説明は v1 の「原稿の外部送信と学習への利用」に従い、ストア掲載情報・プライバシーポリシー・設定画面に、編集に応じて原稿が自動的に繰り返し送信されることを明記する。専用の同意ダイアログや指摘パネル内の説明は設けない。手動送信だけを説明していた既存利用者には、変更を通知したうえで設定画面から自動起動を有効にできるようにし、更新だけでは自動送信を開始しない。

自動起動で結果が繰り返し更新されるため、v1 の「再び見直したときだけ指摘と状態が作り直される」契約は変わる。自動起動では結果の更新が書き手の操作なしに起きるので、更新で書き手の採否判断（適用済み・削除）を消さないことをこの機能側で保証する（Acceptance Criteria 参照）。

起動判断の方式は未決であり、コード判定と Jev による意味判断を評価計画で比較して決める。Jev を採用する場合、原稿（またはその差分）は校閲用 LLM とは別の外部送信先（TypeSafe）へ送られ、提供者側で別途 API key と費用を持つ。採用前に学習への利用と保存の条件を確認し、設定画面とポリシーに記載する。標準モードに使う場合は、起動判断への送信も学習不使用の条件を満たす必要がある。自動起動に利用者の BYOK を要求しない方針のため、判定費用が標準モードの上限なし運用に見合わなければ Jev は BYOK 限定または不採用とする。

### Goals

- 書き手が「見直す」を押さなくても、推敲の区切りで指摘が得られる
- 書き途中への起動・過剰な起動を抑え、執筆中の表示更新・フォーカス・スクロールを妨げない
- 標準モードで恒常的な回数上限を設けなくて済む程度に、1起動あたりの送信量と費用を抑える（異常時の安全弁は残す）
- 編集前の原稿に対する指摘を、現在の原稿への指摘と誤認せずに判断できる
- 自動起動による結果の更新で、書き手が行った採否の判断（適用済み・削除）を消さない

### Non-Goals

- 指摘の自動適用（適用は常に書き手の明示操作。v1 と同じ）
- 校閲そのものの品質・指摘種別の変更（v1 の範囲）
- 「見直す」手動起動の廃止（自動と併存する）
- 外部送信専用の同意ダイアログ、指摘パネル内での送信・学習への利用に関する説明、別途ログインの追加
- Jev の採用を前提とすること（採否は評価計画の結果で決める。見送った場合も本 PRD は成立する）

## Glossary

正本は repo root `AGENTS.md` の `## Glossary`。この機能内に閉じる語:

- **起動判断（trigger decision）**: 原稿の状態を見て校閲を走らせるかを決める判定。コード判定・意味判断（Jev）のいずれかが担う
- **文書バージョン（draft version）**: 校閲対象となった時点の原稿の版。結果が現在の原稿に対するものかを区別するために使う
- **歯止め（cap）**: 自動起動の頻度・回数・連続失敗に対する上限。費用と送信頻度の抑制と、失敗の連鎖防止を兼ねる

## Acceptance Criteria

起動とタイミング:

- [ ] 原稿の内容が変わる編集を続けたあと、書き手が何も押さなくても校閲が起動する
- [ ] 連続した編集中は起動せず、編集が途切れてから起動する（1編集1起動にならない）
- [ ] 原稿の内容が変わらない操作（読み直し・カーソル移動・スクロール・指摘の「削除」など、パネル上の操作全般）では起動しない
- [ ] IME の変換確定前の入力では起動しない
- [ ] 自動起動の実行中・完了時に、パネルの自動展開・フォーカス移動・スクロール移動は起きない。新しい指摘が届いたことは目立たない表示で分かる
- [ ] 起動判定は原稿内容の変化そのものではなく、変化の発生源で区別する。書き手の編集のみが起動対象で、拡張自身が行う「適用」「元に戻す」による原稿の変更だけでは直ちに再校閲が起動しない（適用のたびに校閲が連鎖しない）

バージョンと古い結果:

- [ ] 校閲の実行中に原稿が編集された場合、返ってきた結果は古い版のものとして区別できる表示になるか、最新版への再校閲に置き換わる。古い版の指摘を現在の原稿への指摘と同じ見え方で表示しない
- [ ] 自動起動が有効で失敗・上限到達していない条件では、最後の編集から一定時間（既定値は実装時に決め、評価結果で調整する）以内に最新版の原稿への校閲が開始される。実行中・完了・失敗は区別して分かる
- [ ] 同時に走る校閲は原稿ごとに1つまで。実行中に新しい起動条件を満たしても多重に走らない
- [ ] 校閲の実行中に手動で「見直す」を実行した場合、手動が優先される（実行中の自動校閲を中断するか、その結果を破棄して最新版で走り直す）。利用者が押した操作が無視されない
- [ ] 先に始まった校閲の結果が後から届いても、より新しい版の原稿に対する結果を古い結果で上書きしない
- [ ] 同一の原稿を複数のタブで開いた場合でも、校閲は1系統だけ起動し費用が倍にならない
- [ ] 自動起動による結果の更新で、書き手が「適用済み」「削除」にした指摘の判断が消えない。同一の指摘が再び返ってきた場合は未対応に戻さず従来の状態を保持する（再指摘として区別するか、従来の状態のまま残すかは実装時に決める）。次の結果に含まれなくなった指摘も、適用済み・削除済みの履歴として残る
- [ ] 「同一の指摘」は、指摘の種類と対象箇所の原文が一致するものとする。書き手の編集で対象箇所が言い換え・分割されて原文が一致しなくなった指摘は別の指摘として扱い、過去の採否判断は引き継がない（古い判断で新しい指摘を隠さないため）。一致判定は原文一致を原則とし、前後文脈の利用は原文だけで一意に決まらない場合の補助に限定する

失敗と制御:

- [ ] 通信失敗・API エラー時に理由と再試行の手段が示される。失敗後に自動起動が黙って連鎖的に再試行し続けない
- [ ] 失敗の種類で扱いが分かれる。認証失敗・設定不足は利用者が設定を直すまで自動起動せず、案内は繰り返し表示しない。通信断・タイムアウト・レート制限は次の起動条件で再試行し、連続して失敗した場合は上限回数で自動起動を停止してその旨と復帰方法を示す
- [ ] 自動起動が停止した場合でも、手動の「見直す」は引き続き試せる
- [ ] 書き手は自動起動を一時停止・再開できる。一時停止は新規の起動を止めるもので、実行中の校閲や既に表示された指摘を消さない
- [ ] 自動起動の有効・一時停止は特定の記事やタブではなく拡張全体に作用し、ページの再読み込みや別記事への移動を跨いで保持される
- [ ] 標準モード・BYOK のいずれでも、利用者に追加の key を求めずに動く。起動判断に外部の判定サービス（Jev 等）を使う場合も、標準モードでは利用者の key を要求しない方式にするか、判定サービスなしで自動起動が成立する経路を残す
- [ ] 標準モードでは恒常的な回数上限を設けない方式を目指す。安全弁（提供者側のレート制限・異常検知による停止）が発動した場合は、その旨と再開時期が分かる
- [ ] 校閲に必要な設定（BYOK の API key 等）が未完了の状態では自動起動せず、案内は既存のエラー導線に従う。編集のたびに案内が繰り返し表示されない

外部送信の説明と学習への利用:

- [ ] ストア掲載情報・プライバシーポリシー・設定画面には、編集に応じて原稿が自動的に繰り返し送信されることと、一時停止・無効化できることが明記される
- [ ] 手動送信だけを説明していた既存利用者には変更を通知し、設定画面から自動起動を有効にできる。更新だけで自動送信は始まらない
- [ ] 自動起動の開始時・実行時に外部送信専用の同意ダイアログを表示せず、指摘パネルに送信・学習への利用の説明を追加しない
- [ ] 起動判断に外部の判定サービス（Jev 等）を使う場合、送信する原稿・差分と送信先、学習への利用・保存の条件を設定画面とポリシーで確認できる。標準モードでは起動判断への送信も学習不使用の条件を満たす。判定サービスへの key 未設定や失敗でも、校閲本体が使える経路（手動「見直す」等）が残る

## Success Metrics

- コアアクション: 推敲中に返ってきた指摘の少なくとも1件に「適用」「元に戻す」「削除」のいずれかを行う（自動起動・手動起動を問わない。通知・リマインド経由の来訪は除く）
- 期待頻度 (cycle): 記事を書くたび（作者の現在のペースで月数本）
- 数える対象: 自分から執筆を始め、自動起動が有効な状態でコアアクションを行った書き手の数
- 主指標: 初回にコアアクションを行った書き手のうち、観測期間内に別の記事でもコアアクションを行った割合。観測期間は記事を書く頻度（30日）に合わせる

補助指標（主指標の解釈に使う）:

- 自動起動で表示された指摘への反応率（アクションした指摘数 / 自動起動で表示された指摘数）。読む前に更新で消えた指摘は分母から除き、除外した件数自体も記録して更新頻度の異常を検出できるようにする
- 記事あたりの校閲起動回数と送信トークン量（校閲本体・判定サービス・失敗・中断の送信をすべて含む）。手動運用時の見直し回数・費用と、記事の長さ・執筆時間を揃えた比較で、増えていないことを確認する

v1 と同様、計測基盤が無い間の初期評価は作者自身の利用記録で行う。

## 評価計画（起動判断の方式）

起動判断の方式（コード判定 vs Jev）は未決のまま本 PRD を進めるため、実装着手前に次の比較を行い、結果を本ディレクトリの `result.md` に記録する。

### 比較対象

- **(a) コード判定**: 編集イベント・無入力時間・文量やブロックの変化など、観測可能な信号だけで起動を決める
- **(b) Jev 判定**: 原稿の差分や直近の段落を Jev へ送り、「いま校閲を走らせる意味があるか」を判定させる。コード判定で候補時機を絞ってから Jev で最終判断するハイブリッドも (b) の変形として含める

### 分母と正解ラベル

- 作者の既存記事の推敲過程を模した編集系列を最低10系列用意する（書き途中の連続入力・完成直前・読み直しのみ・大改稿を含める）。系列は result.md に一覧を残し、追加した場合も追記する
- 方式を実行する**前に**、各系列の「起動してほしい区切り点」と「起動してほしくない機会」に正解ラベルを付ける。「機会」は編集イベント単位ではなく編集区間（連続入力のまとまり）単位で数える。区切り点から起動が許容される遅延の上限と、同一区切りでの重複起動の数え方も事前に固定する。誤起動率は「誤起動数 / 起動してほしくない機会の数」、取りこぼし率は「区切りで起動しなかった数 / 起動してほしい区切りの数」とする
- 模擬系列での評価後、採用案を作者の実際の執筆（最低1記事）で確認してから実装判断とする

### Go/Kill

- **Jev 採用条件（Go）**: 誤起動率・取りこぼし率の双方がコード判定以下で、かつ少なくとも一方がコード判定の半分以下で厳密に小さい（コード判定が0の指標では改善にならないため、もう一方で改善が要る）。加えて、日本語原稿での判定応答の成功率が95%以上、p95遅延が事前に固定した許容閾値（評価実行前に数値を result.md に記録）以内であること。判定費用は、実測した記事あたりの回数・トークン量から、標準モードで恒常的な上限なしに提供者が負担できる額かを確認する（見合わない場合は BYOK 限定か不採用）。key・費用・追加送信の運用負荷は、改善幅に対して見合うことを判断材料として明記する
- **最低品質ゲート**: 採用経路を問わず、採用する方式は正解ラベルに対する最低品質（誤起動率・取りこぼし率の許容上限。分母確定時に数値を固定して result.md に記録）を満たすことが必須。両案とも満たさない場合、または期限内に確認できなかった場合は、自動起動そのものの仕様を見直して本 PRD に戻る。未確認のまま実装へ進まない
- **Kill 条件**: Jev が Go 条件を満たさない場合はコード判定を採用する（最低品質ゲートを満たすことが前提）
- **試行上限**: プロンプト・閾値の調整は各方式2回まで。比較全体は評価開始から2週間を上限とし、それを超えた場合はコード判定案が最低品質を満たしていればそれを採用、満たしていなければ PRD に戻る
- 判定フェーズに入った後は正解ラベル・閾値・遅延の許容値を変更しない。やむを得ず変更した場合は理由を result.md に記録し、変更後の基準で再評価する

### 前提

- Jev の評価には TypeSafe の API key が要る（現状未導入）。評価用の key と runtime は評価時に用意し、評価は本番コードに組み込まず分離した計測で行う
- Jev 採用時の key・費用は提供者側の負担とし、利用者には要求しない（Overview の方針に従う）。判定費用が標準モードの上限なし運用に見合わない場合は、Jev は BYOK 限定または不採用とする

## 未決事項

- 標準モードの自動起動時の検索も v1 の DuckDuckGo 方針に従う。編集に伴う反復検索が取得成功率・遅延に与える影響と、検索の連続失敗時に検索の再試行を停止する条件を評価する。検索を停止しても、検索を必要としない校閲は継続できる
- 起動判断の方式（評価計画の実施待ち）
- Jev 採用時の適用範囲（標準モードでも使うか、BYOK 限定にするか。判定費用次第）
- 設定画面・ストア掲載情報・プライバシーポリシーの具体的な文言（v1 の外部送信・学習への利用の方針に従う）
- Jev の学習への利用・保存の条件（採用前に確認する）
- 安全弁（提供者側のレート制限・異常検知）の具体的な閾値（Gateway 側の費用実測と相談して決める）
- 古い結果の表示形式（区別表示か破棄して再校閲か。AC はどちらも許容する形で記述。実装・prototype で決める）
