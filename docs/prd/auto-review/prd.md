# 校閲の自動起動（auto-review）

関連: [note-inline-review](../note-inline-review/prd.md) / [本文検知の範囲](../multi-surface/research.md) / [アイコンの状態見本](./prototype/README.md)

## Problem

書き手が編集のたびに「見直す」を押す方式では、校閲を始める時期の管理が書き手に残る。起動を忘れると古い指摘が残り、細かく起動すると書き途中の指摘と送信費用が増える。

自動化しても、通知や画面の更新が執筆を遮れば目的を満たさない。書き手が引き受けたいのは、校閲を起動する操作ではなく、指摘を採用するかの判断である。

## 導出

Storyの「原稿にレビューをかけて指摘を見る」の起動を自動化し、「指摘を採用するか自分で判断して直す」に集中できるようにする。

## Overview

確定した本文を開いたときや、編集の区切りで校閲が自動的に行われる。通常の利用では起動ボタンを押さず、必要なときだけ指摘一覧を開いて判断する。結果の到着でパネル・入力位置・スクロールは動かない。

小さな変更のたびに原稿全文をLLMへ繰り返し送信せず、変更と必要な文脈に応じた範囲を見直す。部分的な確認と文書全体の確認は区別し、全体の整合性を見直す機会も設ける。送信範囲や起動時期を決める具体的な方式は実装・検証で選ぶ。

右下のアイコンは、中央にロゴを残し、外周のボーダーで指摘の消化率を静かに示す。未判定は外周の点線で表す。処理の進捗を表す表示や、通知ドット・件数バッジ・点滅・音・自動展開で注意を引かない。修正の適用は引き続き書き手が判断する。

### Goals

- 通常の執筆で校閲を起動する操作を不要にする。
- 執筆を妨げず、編集後の指摘を適切な時期に更新する。
- 送信量と費用を抑えながら、必要な校閲を受けられるようにする。
- 指摘をどこまで扱ったかを、右下の円形表示で把握できるようにする。

### Non-Goals

- 原稿の生成、指摘の自動適用。
- 校閲の判定基準・指摘種別・対応する入力方式の拡張。
- 起動判断へのAI導入を必須にすること。

## Glossary

- **消化率**: 現在の原稿に対応する指摘のうち、書き手が適用または削除した割合。閲覧は含めず、文章の品質や校閲処理の進捗を表さない。複数箇所を持つ指摘は、未対応の箇所が残れば未対応とする。
- **確認範囲**: 校閲結果が有効な原稿の範囲。部分的な確認が終わっても、文書全体の確認が終わったことにはしない。

## Acceptance Criteria

- [ ] 書き手が確定した本文を開いたときや、編集の区切りで、パネルや起動ボタンを操作せずに校閲を受け取れる。
- [ ] 書き手が入力・IME変換・読み返しを行う間、過剰な起動や画面の自動展開、フォーカス・選択範囲・スクロールの移動に妨げられない。
- [ ] 書き手が未判定の画面を開いてもエラーや自動送信は起きず、必要なときだけ最大の対応可能な領域をその回限りで見直せる。本文が無い画面では校閲を始めない。
- [ ] 書き手が長い原稿の一部を直すと、停止のたびに全文を送信されずに指摘が更新される。部分確認を全文確認済みとは表示せず、文書全体の整合性も適切な区切りで見直される。
- [ ] 書き手が校閲中に編集しても古い対象への結果が現在の結果を上書きせず、部分的な更新で範囲外の有効な指摘が失われない。
- [ ] 書き手が指摘を適用・削除した判断は結果の更新後も保持され、別記事・別箇所・新しい指摘へ誤って引き継がれない。拡張による適用だけで再校閲が連鎖しない。
- [ ] 書き手が指摘を扱うと円形表示に消化率が反映され、指摘なし・全件対応・更新待ちを区別できる。新しい指摘が加わっても採否の履歴は消えず、閲覧だけでは消化率が上がらない。
- [ ] 書き手が一時停止・再開を選べ、失敗や確認が必要な場合も執筆を続けながら自分のタイミングで原因を確認して復帰できる。

## Non-Functional Requirements

- 同じ校閲範囲の重複送信、過剰な並行実行、失敗時の無限再試行を防ぎ、校閲本体・検索・起動判断を含む総費用を確認する。
- 標準モードとBYOKで、パネルを閉じた通常の執筆でも動く。必要な確認が対話を要求する場合は、執筆を遮らず利用者の操作を待つ。
- 自動送信の説明、一時停止・無効化、学習利用の扱いは既存の外部送信方針に従う。既存利用者には説明と有効化の機会を設け、更新だけで自動送信を始めない。
- 表示は既存のデザインに合わせ、キーボード操作・読み上げ・reduced-motionに対応する。

## Success Metrics

記事を書くたびに、自動で届いた指摘を少なくとも1件、適用または削除した書き手が、別の記事でも同じ行動を行う割合を見る。対象は自分から執筆を始めた書き手とし、初期評価は作者自身の利用記録で行う。

起動操作の不要さ、執筆への割り込み、不要な送信、記事あたりの総費用も確認する。消化率100%や提案の採用率自体は成功指標にしない。

## 方式選定の参考

起動判断には、ルールだけで十分な場合と、書き途中かどうかなどの意味判断が有効な場合がある。必要な品質・遅延・費用を満たす最小の構成を選び、AIが不要なら追加しない。

意味判断が必要なら、Workers AIの[Clef / Clef-flash](https://blog.cloudflare.com/clef-decision-models/)と、候補に挙がっていた[TypeSafe Jev](https://docs.typesafe.ai/concepts/how-to-build-with-system-one)を比較対象にする。起動判断のために全文を別サービスへ毎回送る方式は避け、モデルの採用で送信許可や本文の確定判定を変えない。
